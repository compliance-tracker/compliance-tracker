## Tech stack (decided, don't change without discussing)

- **Language:** Java 21 (LTS — deliberately not 25/26)
- **Framework:** Spring Boot 4.1.0
- **Build tool:** Maven
- **Database:** PostgreSQL 16 (Docker locally), schema managed by **Flyway** migrations (`src/main/resources/db/migration/`) — not `ddl-auto`
- **Queue:** AWS SQS — LocalStack locally/CI, real AWS at deployment
- **Auth:** Spring Security + JWT (stateless, `jjwt` library — chose JWT over session cookies since the frontend is a separate origin/app, not server-rendered)
- **Deployed later:** AWS ECS/Fargate + RDS (not done yet — blocked on having an AWS account)

## Known gotchas already hit — watch for these recurring

- **`pom.xml` dependencies have gone missing/gotten reset more than once** during editing — always double check the full `<dependencies>` block after any edit, rather than assuming a prior edit persisted.
- **`application.properties` similarly got wiped back to near-empty once** — same caution applies.
- **New Java files must be placed inside the correct package folder, matching the `package` declaration** — a file placed in the wrong directory fails to compile with confusing "cannot find symbol" errors. As of issue #90, this is **no longer one flat folder** — the app is split package-by-feature under `src/main/java/com/chrainx/compliance_tracker/`: `auth/`, `business/`, `config/`, `notifications/`, `queue/`, `rules/` (pre-existing), plus the root itself for `ComplianceTrackerApplication`/`HelloController`. A new file needs both the right directory *and* the matching `package com.chrainx.compliance_tracker.<feature>;` line — get either wrong and it's the same cryptic compile error as before. Test packages mirror this exactly.
- **A package reorganization needs a check for cross-file package-private (no-modifier) access before moving anything** — a package-private field/method used by another class in the same package silently breaks the moment that access crosses a package boundary, with no compiler hint pointing at "here's why" beyond a generic "cannot find symbol." `grep` for method/field declarations lacking `public`/`private`/`protected` across the affected files first (issue #90 turned up exactly one, `LoginRateLimiter`'s inner `windowExpired()` — safe since it's only used within that same file, which moved as one unit).
- **The compiler is the most reliable guide for adding cross-package imports during a bulk move, not manual reasoning** — run `./mvnw compile`/`test-compile` repeatedly, add the exact import each "cannot find symbol" error names, repeat. Watch for **duplicate imports** on any file that already had an explicit cross-package import predating the move (issue #90 hit this in `RuleEngine.java`/`RuleEngineTest.java`, both already in the `rules` subpackage importing `Business`/`WorkPass` from the old flat package) — the compiler correctly rejects the stale old-path import once that class no longer exists there, and it looks identical to a "forgot to add the import" error until you actually read which import is broken.
- **DevTools auto-restart doesn't always reliably pick up `application.properties` changes** — do a full manual stop/restart if a config change doesn't seem to take effect.
- **When verifying anything, check actual state directly** (`docker exec ... psql ... "\dt"`, `aws sqs receive-message`, etc.) over trusting terminal/log output alone.
- **Spring Boot 4.1 renamed Jackson's Java packages**: `com.fasterxml.jackson.*` → `tools.jackson.*` (Jackson 3). Also `writeValueAsString` now throws an *unchecked* `JacksonException`, not the old checked `JsonProcessingException`.
- **Spring Boot 4 split autoconfiguration into per-technology starter modules.** Adding a library's core jar alone (e.g. plain `flyway-core`) no longer triggers its autoconfiguration — need the dedicated starter (`spring-boot-starter-flyway`). If something silently doesn't activate with no error, check whether Spring Boot 4 moved its autoconfiguration to a separate module before assuming the code is wrong.
- **`@Transactional` doesn't work via self-invocation** (a method calling another `@Transactional` method on `this` within the same class) — Spring's proxy isn't involved, so it's silently a no-op, no error raised.
- **`@SpringBootTest` boots the entire real app, including real `@Scheduled` jobs.** Once a background poller existed (`ReminderWorkerService`), it started racing integration tests for messages they'd just enqueued. Fixed via `SchedulingConfig` (gated behind `scheduling.enabled`) + a `test` Spring profile disabling scheduling in `@SpringBootTest` classes.
- **LocalStack versions newer than `3.8.1` require a paid license/auth token even for SQS** on the free community tier — pin to `3.8.1`.
- **LocalStack's queue state is in-memory and does not survive a container restart** — re-run queue/DLQ creation any time LocalStack was stopped, even if reusing the same container.
- **`gh` CLI auth needs scopes added as they come up** — the default token only has `repo`/`read:org`/`gist`. Creating a GitHub Project needed `project` added (`gh auth refresh -h github.com -s project`), deleting a repo needed `delete_repo`. Each is a device-code flow requiring the user to approve in a browser — can't be done silently.
- **AWS CLI against LocalStack needs dummy credentials present** (`AWS_ACCESS_KEY_ID=test AWS_SECRET_ACCESS_KEY=test`) even though LocalStack doesn't actually check them — the CLI itself refuses to run with none configured at all.
- **This repo moved GitHub ownership**: originally `Chrainx/compliance-tracker`, transferred to the `compliance-tracker` organization (see root CLAUDE.md). Local remote was updated (`git remote set-url origin ...`) — if a stale remote URL ever causes push/fetch confusion, that's why.
- **Spring Security's default rejection status is 403, not 401**, for a request with no authentication at all — needs an explicit `AuthenticationEntryPoint` (see `SecurityConfig`) to get the semantically-correct 401. Don't assume the default is right without checking.
- **`TestRestTemplate` moved out of `spring-boot-starter-test` in Spring Boot 4** — separate module (`spring-boot-resttestclient` + `spring-boot-restclient`, both needed), new package (`org.springframework.boot.resttestclient.TestRestTemplate`), and `@SpringBootTest` no longer auto-provides it — needs `@AutoConfigureTestRestTemplate` explicitly. Third Spring Boot 4 modularization surprise this project has hit (after Jackson's package rename and Flyway's starter requirement) — the pattern now: if something that used to "just work" silently doesn't, check whether it moved to its own module before assuming the code is wrong.
- **`@JsonIgnore` matters on any entity relationship that could reach sensitive data** — `Business.owner` (a `User`, which has a password hash) would otherwise get serialized straight into API responses. Caught this while building auth, before it shipped as a bug, not after.
- **`@RequestBody` binding straight onto a JPA entity is dangerous if the entity's `id` field isn't guarded** — a client can supply their own `id` in the body, and `JpaRepository.save()` silently does an UPDATE (not INSERT) whenever that id is non-null and exists, overwriting someone else's row. Found and fixed as a real, confirmed IDOR in `createBusiness` (issue #66) — auth alone (knowing *who* you are) doesn't protect *which row* you're allowed to touch. Fixed properly, not just defensively, by issue #46: `BusinessController`/`WorkPassController` now bind `BusinessRequest`/`WorkPassRequest` (no `id` field at all), not the entities directly — nothing left to remember to clear.
- **A "recurring" rule computed from a single stored date needs to actually recompute from `referenceDate`, not just apply a fixed offset once** — GST F5 got this right from the start (`calendarQuarterEnd(referenceDate) + 1 month`, so it naturally tracks whatever quarter `today` is in). ACRA Annual Return didn't: `financialYearEnd.plusMonths(7)` was a one-time calculation with no dependency on `referenceDate` at all, so once that single deadline passed there was no way to get next year's. Fixed (issue #27) via `nextAcraDeadline`, which keeps adding a year until the result isn't before `referenceDate`. Worth checking any *new* rule against this same question: does it actually use `referenceDate` to find the next occurrence, or does it silently assume "today" is always before the one date it computes?
- **Spring MVC's internal forward to `/error` is itself subject to `SecurityConfig`'s rules** — a valid token hitting a malformed path param or an unmapped path was getting misreported as `401` instead of the real `400`/`404`, because `/error` wasn't in the `permitAll()` list and the forwarded dispatch didn't carry authentication through. Fixed (issue #67) by adding `/error` to `permitAll()`. Not a security hole (no response body leaked either way), but a correctness/DX trap: don't assume a 401 means "auth is broken" without checking whether the *real* failure is somewhere else entirely and just got relabeled on the way out.
- **A new `@RequestBody Entity` endpoint should apply the #66 id-clearing fix from day one, not after the fact** — `WorkPassController.createWorkPass` (#24) has the exact same `@RequestBody WorkPass` shape that caused the original IDOR, so `workPass.setId(null)` was written in from the start rather than shipping the same bug again and fixing it later.
- **Two `@ConditionalOnProperty`-gated beans implementing the same interface, one as the default** — `NotificationSender` now has `LoggingNotificationSender` (`matchIfMissing = true`, active whenever `notifications.channel` isn't explicitly `email`) and `EmailNotificationSender` (`havingValue = "email"`). This pattern (a safe zero-config default + an opt-in real implementation behind one property) is worth reusing for any future integration that needs real credentials CI/local dev shouldn't require.
- **Every `spring.mail.*` value is env-var overridable, not just username/password** — `MAIL_HOST`/`MAIL_PORT`/`MAIL_SMTP_AUTH`/`MAIL_SMTP_STARTTLS`, defaulting to real Gmail SMTP. This is what lets the exact same config point at [Mailpit](https://mailpit.axllent.org) (`docker run axllent/mailpit`, real local SMTP + web UI, zero credentials) for previewing emails locally instead of a real account — see `docs/notifications.md`.
- **`jwt.secret`/`spring.datasource.password` were plain values committed in `application.properties`** — fixed (issue #40) via `${JWT_SECRET:default}`/`${DB_PASSWORD:default}` placeholders, same pattern as the mail env vars. Important nuance: this stops *new* deployments from reusing the committed default, it does **not** erase the old value from git history — that requires deliberately rewriting history (destructive, force-push, breaks other clones), not done as part of this fix. Practical exposure today is ~zero since nothing real has ever been deployed with these values, but whoever deploys for real must generate fresh ones (`openssl rand -base64 32`), never reuse the placeholders.
- **A `findByEmail` check followed by a separate `save()` is not atomic** — two concurrent requests can both pass the check before either commits, and the DB's unique constraint (not the check) is the real enforcement point. Found as a genuine, reproducible race in `AuthController.register` (issue #42) — fixed by catching `DataIntegrityViolationException` around `save()` and returning the same `409` the sequential-request case already does. Any other "check then act" pattern against a uniqueness constraint elsewhere in the codebase has the same shape of bug lying in wait.
- **`static` on a field inside an `@Component` looks harmless but breaks test isolation** — `@Component` already gives the whole running app one shared instance for free; `static` is a separate, lower-level Java rule that shares a field across *every* instance ever constructed in the JVM, including ones tests create directly with `new SomeComponent()` bypassing Spring entirely (exactly the pattern `LoginRateLimiter`/`TokenBlocklist` tests rely on for isolation). Caught this while building `TokenBlocklist` (issue #41) before it shipped, not after.
- **A security filter (`JwtAuthenticationFilter`) should never set its own response status and short-circuit the chain** — its only job is deciding whether to populate the `SecurityContext`; `SecurityConfig`'s `authorizeHttpRequests` + `AuthenticationEntryPoint` own rejecting requests, exclusively. Setting a status directly and skipping `filterChain.doFilter(...)` risks skipping other filters still needed further down (CORS handling, given this project has already hit real CORS issues once). A revoked/expired/malformed token should all be treated the same passive way: don't authenticate, let the request fall through.
- **Fixed the `SqsDispatchIntegrationTest` flakiness (issue #75)** — its `receiveMessage()` had no `waitTimeSeconds` set (SQS short polling, which doesn't guarantee returning every currently-available message on one call), unlike `ReminderWorkerService`'s real poll (`waitTimeSeconds(5)`, long polling). Added `.waitTimeSeconds(5)` to the test to match. If a *different* SQS-touching test ever shows this same "assert on messages, sometimes empty" shape, check for a missing `waitTimeSeconds` first.
- **LocalStack's queue state persists across everything pointed at the same running container** — a real `spring-boot:run` session, curl-driven manual verification, and `@SpringBootTest`s all share the exact same queue unless something purges it. A long session mixing extensive manual live-testing with test runs piled up 44 unconsumed messages in the local `compliance-reminders` queue (issue #75's investigation), which made `ReminderWorkerIntegrationTest` fail consistently — not a code bug, just a backlog burying the test's own message. Check the queue's actual depth (`aws --endpoint-url=http://localhost:4566 sqs get-queue-attributes --queue-url <url> --attribute-names ApproximateNumberOfMessages`) before assuming a real SQS-integration-test failure is a real bug; `aws sqs purge-queue` is safe to clear local dev/test pollution.
- **A singleton bean holding mutable state (`LoginRateLimiter`) is shared across every test in the same cached `@SpringBootTest` context** — and since `TestRestTemplate` calls all originate from the same loopback IP, one test's failed login attempts silently count toward another test's rate-limit budget if test order isn't controlled. Fixed in `AuthIntegrationTest` via `@TestMethodOrder` + `@Order(1)` (run the rate-limit test first, before anything else can pollute the shared IP's count) plus `@DirtiesContext(methodMode = AFTER_METHOD)` (rebuild the context, and the bean, afterward so it doesn't pollute what runs next). Worth remembering for any future stateful singleton tested via real HTTP calls.
- **MVC-level CORS (`WebMvcConfigurer.addCorsMappings`) never runs for a request Spring Security's own filter chain rejects early** (e.g. `HttpStatusEntryPoint` committing a 401 for a missing/expired token) — that response has no `Access-Control-Allow-Origin` header, which a browser's `fetch()` doesn't surface as a readable 401, just an opaque "blocked by CORS policy" network failure with no status code accessible to JS. curl/Postman never catch this since CORS is purely browser-enforced. Found live via Playwright while building frontend #17 (issue #83) — fixed by moving CORS to Security-level (`CorsConfigurationSource` bean + `.cors(Customizer.withDefaults())` in `SecurityConfig`), which registers Spring Security's own `CorsFilter` at the very front of the chain, before the entry point can reject anything. Any future security-rejection path (a new custom filter, a new entry point) needs to stay ahead of — or otherwise not bypass — this CORS filter, or the same gap reappears.
- **When a response shape genuinely changes (array → object, not just a field added/removed), every integration test deserializing it fails loudly and immediately** — a real, useful signal, unlike the silent "still compiles and coincidentally passes" version of this problem hit twice before (see the DTO-separation gotcha above). Hit this converting `GET /api/businesses`/`GET /api/businesses/{id}/work-passes` from a bare array to a `PageResponse<T>` envelope (issue #49) — every test deserializing the old array shape threw `MismatchedInputException: Cannot deserialize ... from Object value (token JsonToken.START_OBJECT)` right away. Fixed by switching to `ParameterizedTypeReference<PageResponse<T>>` (required for any generic type through `RestTemplate`/`TestRestTemplate` — a plain `.class` token loses the `<T>` to erasure).
- **A genuinely breaking API response-shape change against an already-integrated live frontend needs an explicit decision, not a silent default** — issue #49's pagination change was discussed with the user first (ship the real shape now, frontend catches up in its own follow-up PR — the same pattern already used for #24/#15, #25/#16, #26/#17) rather than assumed. Don't quietly compromise a backend design to avoid a temporary frontend break without asking.
- **Adding `@Transactional` to a controller method changes *when* the SQL from any repository calls inside it actually executes, not just whether a rollback is possible.** Without it, each Spring Data repository call (e.g. `save()`) runs in its own transaction and its `INSERT`/`UPDATE` executes synchronously, right there — so a `try { repo.save(x); } catch (DataIntegrityViolationException e) { ... }` catches a real constraint violation exactly where it's written. With `@Transactional` on the caller, that inner call *joins* the existing transaction instead (Spring's default `REQUIRED` propagation), so Hibernate can legally defer the actual write (write-behind) until commit — which happens in the `@Transactional` proxy *after* the method body already returned, past any `try`/`catch` entirely. Found live building #36: naively adding `@Transactional` to `AuthController.register` (to match the genuinely-needed additions on `forgotPassword`/`resetPassword`) silently broke issue #42's registration-race handling — both concurrent requests started coming back non-200 instead of the expected one-200/one-409 split. Fixed by NOT adding it to `register` (it doesn't need it — no derived delete query there). Check whether a method's existing exception handling relies on synchronous repository execution before reflexively adding `@Transactional` to it.
- **A Spring Data JPA *derived delete/modify* query (e.g. `deleteByUserId(Long)`) needs an actual transaction already open on the calling thread — unlike the inherited `save()`/`delete()` methods, which `JpaRepository` already wraps in their own transaction internally.** Calling one from a plain (non-`@Transactional`) `@RestController` method throws `InvalidDataAccessApiUsageException: No EntityManager with actual transaction available for current thread`. Found live building #37's password reset flow (`PasswordResetTokenRepository.deleteByUserId`) — fixed by adding `@Transactional` to `AuthController.forgotPassword`/`resetPassword`. A derived *read* query (`findByX`) doesn't have this problem; only delete/modify ones do. Check for this whenever adding a new derived delete method to any repository.
- **An idempotency-key race isn't just "catch the DataIntegrityViolationException and move on" the way issue #42's registration race was** — #42's loser had nothing to clean up (the failed insert *was* the side effect). For `createBusiness`'s idempotency key (issue #61), each concurrent thread has already created a real, separate row (the `Business`) *before* the key-insert race resolves — silently swallowing the exception the #42 way would leave the loser's business behind as an orphaned duplicate, exactly what the feature exists to prevent. The fix: on that exception, delete the just-created row and return whichever row the winning insert actually claimed. Any future "idempotency key guards an insert that itself has side effects beyond the row being inserted" situation needs this same cleanup-on-loss shape, not the simpler #42 pattern.
- **A `@RequestBody Entity` shape defends against IDOR by remembering to clear the `id` field before `save()` — a dedicated request DTO with no `id` field at all prevents it structurally instead, with nothing to remember.** The original #66 fix (`business.setId(null)`) worked, but relied on every future `@RequestBody Entity` endpoint remembering the same defensive line (#24's `WorkPassController.createWorkPass` did remember — but only because the pattern was fresh). Issue #46 replaced both `Business`/`WorkPass`'s direct entity binding with `BusinessRequest`/`WorkPassRequest` (no `id` field, period) — verified live that a client-supplied `id` in the request body is now just silently ignored as an unrecognized JSON field, not defended against by code that could someday be skipped.
- **When entities stop being serialized directly (a DTO split), sweep every test that constructed the entity as a request body or deserialized a response into the entity type** — they'll likely still compile and even still pass, purely by coincidence if the DTO's field names match the entity's, which silently defeats the point of the split: a test still targeting the old entity type can't catch a future DTO/entity shape mismatch. Hit this doing #46 — `BusinessIntegrationTest`/`WorkPassIntegrationTest` still worked against `Business.class`/`WorkPass.class` after introducing `BusinessResponse`/`WorkPassResponse`, and needed deliberately switching to the new DTOs to actually prove anything again.
- **Spring checks `@ExceptionHandler` methods in a `@RestControllerAdvice` before its own default exception resolution runs** — a blanket `@ExceptionHandler(Exception.class)` would intercept framework-level exceptions like `MethodArgumentTypeMismatchException` (malformed path variable) and `NoHandlerFoundException` (unmapped path) *before* Spring's own default handling gets a chance to correctly turn them into 400/404 (see issue #67's regression tests in `AuthIntegrationTest`), silently downgrading them to a generic 500 instead. Deliberately did NOT add a catch-all handler while building the consistent error-response format (issue #47) for exactly this reason — scoped the `GlobalExceptionHandler` to only `MethodArgumentNotValidException`, the one case that actually needed it. If a future catch-all is ever added, it needs to explicitly re-handle (or exclude) these framework exception types, not just assume "more coverage is strictly better."
- **A controller method can only return `ResponseEntity<?>` (not a concrete type) once its error path needs to return a body of a genuinely different type than its success path** — e.g. `ResponseEntity<AuthResponse>` can't also return an `ApiError` body; Java generics won't allow one method to declare two unrelated concrete return types. Widening the return type to `ResponseEntity<?>` (done for 10 methods across `AuthController`/`BusinessController`/`WorkPassController` in issue #47) breaks every mocked-level test that declared a concretely-typed local variable to receive the response — fix by widening the test's local variable to `ResponseEntity<?>` too, plus a small private cast-helper per test class for the tests that inspect a success response's body fields.
- **`@Valid` is only enforced by Spring MVC's argument resolution during a real HTTP request-body bind** — calling a controller method directly in Java (the pattern `BusinessControllerTest`/`WorkPassControllerTest` use against mocked repositories) never triggers it at all, so a mocked-level test can never prove a `@Valid`/Bean Validation annotation actually works, only a real `TestRestTemplate` call through the real `DispatcherServlet` can (issue #20). Same category of gap as `AuthIntegrationTest` already existing specifically to prove `SecurityConfig`'s filter chain works — validation joins the list of things that need a real HTTP integration test, not a mocked one, to be genuinely proven.
- **A new input-validation rule on a widely-used endpoint needs a sweep of every test fixture that hits it for setup, not just the tests about the new rule itself** — adding a minimum password-strength check to `AuthController.register` (issue #43) broke `AuthIntegrationTest`/`BusinessIntegrationTest`/`WorkPassIntegrationTest` project-wide, because their shared test password (`"a-real-password"`, all letters, no digit) had nothing to do with what those tests actually check — they just needed *a* working account. `grep` the literal value across `src/test` before assuming a validation change is self-contained.
- **A DTO shared between two endpoints with different validation rules for the same-shaped field can't use a Bean Validation annotation for either rule** — `AuthRequest` (`email`, `password`) is used by both `register` and `login`; a `@Size(min = 8)` on `password` would enforce registration's strength rule on login too, `400`-rejecting any real existing account whose password predates the check. The fix (issue #43) lives as a plain method call inside `AuthController.register` specifically, not an annotation on the shared record. Worth checking for this shape any time a "just add `@Valid`" fix is tempting for a DTO shared across multiple endpoints.
- **`LocalDate.now()` and `@Scheduled(cron = ...)` both silently default to the JVM's own timezone, not any explicit one** — harmless as long as the server happens to run near SGT, a real bug the moment it's deployed somewhere else (this is a Singapore-specific product; every deadline only means anything relative to Singapore's calendar). Fixed (issue #28) via a shared `RuleEngine.SINGAPORE_TIME_ZONE` constant used at every `LocalDate.now(...)` call site, plus explicit `zone = "Asia/Singapore"` on both `@Scheduled` cron jobs (which independently default to server timezone for interpreting the cron expression itself — same root cause, different mechanism, easy to fix one and miss the other).
- **JWT `iat`/`exp` claims only have *second* precision** — two tokens generated for the same subject within the same wall-clock second are byte-identical signed strings unless something else differentiates them. Broke refresh-token rotation for real (issue #26, found live via curl, not hypothetically): revoking "the old" refresh token by exact string match also silently revoked the "new" one just issued to replace it, since a rapid refresh could mint the same string twice. Fixed by adding a random `jti` claim (`.id(UUID.randomUUID().toString())`) to every generated token. Worth remembering for any future code that treats a JWT string as a unique identifier. **This same second-precision claim also bit `User.tokenValidAfter` (issue #96):** comparing a token's `iat` directly against a sub-second `Instant.now()` timestamp could wrongly treat a token minted in the same second as "before" that timestamp once truncated, rejecting a session that should still be valid. Fixed by flooring the `Instant` side to the second (`.truncatedTo(ChronoUnit.SECONDS)`) before comparing — any future code comparing a JWT timestamp claim against a non-JWT (sub-second) timestamp needs the same floor, or risks the same false rejection.
- **Reading a `@ManyToOne(fetch = FetchType.LAZY)` relationship outside an open Hibernate session throws `LazyInitializationException: could not initialize proxy - no session`, and a plain (non-`@Transactional`) repository call's session closes the instant that call returns — before any code afterward that touches the lazy field runs.** Found live (issue #53) inside `SqsDispatchIntegrationTest`/`ReminderWorkerIntegrationTest`: `DeadlineSyncService.findDueSoonAndUnreminded` fetches a list of `DeadlineRecord`s via a plain repository call, then filters them in a `.stream()` that reads each record's lazy `business` field (`record.getBusiness().getLeadTimeDays()`) — by the time that filter runs, the session that loaded the list is already gone. Fixed with `@Transactional(readOnly = true)` on the method, keeping the session open through the whole call, filtering included. Any future code that fetches entities with a lazy relationship and then touches that relationship *after* the initial repository call returns (not inline in a query) needs the same fix.
- **A "find the nearest matching occurrence of a recurring date" search can never detect a violation of a limit longer than the recurrence period itself — a subtle way for a validation check to be silently vacuous.** Building issue #31's 18-month first-FYE cap, the first implementation searched for the nearest occurrence of the FYE month/day on or after `incorporationDate` (to dodge a *different*, real false-positive: a years-old business's stored `financialYearEnd` could hold any past/future year). That search can only ever land within ~12 months of the starting date by construction — so a check built on top of it could *never* register an 18-month violation, no matter the inputs. Two of its own tests failed and caught this immediately; simplified to a plain literal-date comparison instead, which is correct precisely because it's only ever called at the one moment (`createBusiness`, a brand-new business) where the stored date unambiguously *is* the value being validated, not a recurring pattern. Worth checking any future "nearest occurrence of X" logic against the same question: can the thing you're computing structurally ever exceed the threshold you're about to compare it to?
